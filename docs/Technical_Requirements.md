# Benchmark project requirements

This project evaluates whether the Nixtla open-source forecasting libraries (StatsForecast and MLForecast/LightGBM) can match or outperform the production algorithmic forecast on real sales data, at both daily and 15-minute interval granularities.

---

## Glossary

| Term | Definition |
| :--- | :--- |
| Anchor date | The base date that anchors the evaluation window. It is derived from the latest date that has both a valid projection and a valid actual value. |
| Composite UID | A unique identifier for a location, formatted as `{CUSTOMER_ID}_{SITE_ID}`. |
| Evaluation window | The date range over which model predictions are compared to actuals. |
| MLForecast | The Nixtla library that provides machine-learning-based forecasting models, including LightGBM. |
| Nixtla format | The required DataFrame schema for all models: `unique_id` (string), `ds` (datetime), and `y` (float). |
| Baseline_Production | The raw algorithmic projection generated by the Baseline platform. This is the primary baseline. |
| StatsForecast | The Nixtla library that provides classical statistical forecasting models, such as ARIMA, ETS, and Theta. |
| Strict variant | A baseline variant that retains zero-projection rows in evaluation, in contrast to the default variants, which exclude them. |
| Volume tier | A quartile-based grouping (Q1 through Q4) of locations by their mean training-period sales. |
| Weighted Absolute Percentage Error (WAPE) | The primary scale-independent metric for volume-weighted accuracy. |

## Input data

Data is sourced from Snowflake and saved locally before running the benchmarks. The SQL files sample up to `target_location_count` (default: 300) eligible locations.

| File | SQL Source | Frequency | Description |
| :--- | :--- | :--- | :--- |
| `data/input/daily_actual_vs_forecast.csv` | [snowflake/daily_actual_vs_forecast.sql](../snowflake/daily_actual_vs_forecast.sql) | Daily | One row per location per calendar day. |
| `data/input/interval_actual_vs_forecast.csv` | [snowflake/interval_actual_vs_forecast.sql](../snowflake/interval_actual_vs_forecast.sql) | 15-minute | One row per location per 15-minute slot. |

## Data contracts

All internal modules communicate using DataFrames in Nixtla format. The mapping from raw CSV columns to Nixtla columns happens during data loading.

### Nixtla DataFrame schema

| Column | Type | Description | Raw Column (Daily and Interval) |
| :--- | :--- | :--- | :--- |
| `unique_id` | `str` | Composite location identifier | `ENTITY_UID` |
| `ds` | `datetime64[ns]` | Observation timestamp | `DAY_START_TIME` for daily, `INTERVAL_START_TS` for interval |
| `y` | `float64` | Target sales value | `ACTUAL_VALUE` for daily, `NET_SALES` for interval |

## Location eligibility

Locations are included in the benchmark if they have:

- At least 90 days of historical actual sales data with a positive projection, for the daily pipeline (as set by `min_days_with_actuals` in [daily_actual_vs_forecast.sql](../snowflake/daily_actual_vs_forecast.sql)).
- At least 28 days of historical actual sales data with a positive projection, for the interval pipeline (as set by `min_days_with_actuals` in [interval_actual_vs_forecast.sql](../snowflake/interval_actual_vs_forecast.sql)).
- A valid Baseline production projection in the evaluation window.

The daily SQL exposes `IS_GENERATED_BY_MANAGER` as a column but does not filter on it. The Python pipeline uses this flag to construct separate `Baseline_ManagerOnly_Draft` and `Baseline_ManagerOnly_Published` baseline variants (see [Baseline and benchmarking](#baseline-and-benchmarking)).

The interval SQL additionally enforces a coverage guard: locations with fewer than `train_weeks * 7 * 96 * min_coverage_fraction` (the default is 50 percent) 15-minute intervals in the training window are dropped before sampling.

## Evaluation window

### Daily pipeline

The evaluation window is a rolling series of seven-day windows determined by the anchor date.

1. Base anchor selection: the maximum date for which both an `ACTUAL_VALUE` and a `PROJECTION` are present.
2. Rolling windows: controlled by `--rolling-windows N`. Each window extends seven days backward from its anchor.

### Interval pipeline

The evaluation window is defined by the presence of a `Baseline_PROJECTION`.

- Training data: rows where `Baseline_PROJECTION IS NULL`.
- Test data: rows where `Baseline_PROJECTION IS NOT NULL` (typically one week of 15-minute slots).

## Metrics and rounding

All metrics are computed per location, then summarized as a mean or median.

| Metric | Formula | Lower is Better | Key Insight |
| :--- | :--- | :--- | :--- |
| MAE | `mean(|actual - forecast|)` | Yes | Average absolute error in dollars. |
| WAPE | `sum(|actual - forecast|) / sum(actual)` | Yes | Scale-independent and volume-weighted. |
| MAPE | `mean(|actual - forecast| / actual)` | Yes | Mean absolute percentage error; zero-actual rows are excluded from the denominator. |
| RMSE | `sqrt(mean((actual - forecast)^2))` | Yes | Penalizes large outliers heavily. |

### Zero-value policy

- Zero-actual exclusion: when `EXCLUDE_ZERO_ACTUAL_FROM_EVAL=True` (the default), rows where `actual == 0` are excluded before metric computation. This prevents division by zero in WAPE and MAPE, and it avoids skewing MAE and RMSE with closed-day noise.
- Zero-projection exclusion: when `EXCLUDE_ZERO_PROJECTION_FROM_EVAL=True` (the default), the default baseline variants filter to rows where `PROJECTION > 0`. The evaluation then focuses on intervals that the baseline actively forecasted. The strict variants retain zero-projection rows.
- Precision: all metrics use raw float precision; no rounding is applied.

## Preprocessing and logic

The pipelines apply two business-logic assumptions before model training:

1. Closed-day assumption: missing dates or intervals are filled with `y = 0.0`, treating gaps as periods when a location was closed.
2. Outlier clipping: target values are capped at the 99.0th percentile per location (`CLIP_OUTLIER_PERCENTILE = 99.0` in both [daily/config.py](../daily/config.py) and [interval/config.py](../interval/config.py)). Caps are learned from training data only and applied identically to the train and test sets, which prevents leakage.

## Model configurations and tuning

The benchmark evaluates two classes of models, via the StatsForecast and MLForecast libraries.

### StatsForecast models (daily)

| Model | Configuration | Description |
| :--- | :--- | :--- |
| SeasonalNaive_D | `season_length=7` | Repeats the value from the same weekday in the prior week. |
| MSTL_D | `season_length=[7, 365]`, trend = `AutoARIMA` | Multiple seasonal-trend decomposition using LOESS. |
| AutoETS_D | `season_length=7`, `model="ZZZ"` | Error, Trend, and Seasonality state-space models. |
| AutoARIMA_D | `season_length=7` | Automated standard ARIMA model selection. |
| DOT_D | `season_length=7` | Dynamic Optimized Theta model. |

### StatsForecast models (interval)

| Model | Configuration | Description |
| :--- | :--- | :--- |
| SeasonalNaive | `season_length=96` | Repeats the value from the same 15-minute slot one day prior. |
| MSTL | `season_length=[96, 672]`, trend = `AutoARIMA` | Multi-seasonal decomposition at daily (96) and weekly (672) periods. |

### MLForecast (LightGBM) models, daily

Three tiers of LightGBM are evaluated. Hyperparameters are currently tuned manually.

Note: these models are primary candidates for hyperparameter optimization (for example, via Optuna or Ray) to further improve accuracy.

| Tier | Lags | Parameters (Tuned) |
| :--- | :--- | :--- |
| LightGBM_D_Fast | 1, 7, 14, 21, 28 | `n_estimators=200`, `learning_rate=0.05`, `max_depth=6` |
| LightGBM_D_Standard | 1, 7, 14, 21, 28 | `n_estimators=400`, `learning_rate=0.05`, `max_depth=8` |
| LightGBM_D_Accuracy | 1, 7, 14, 21, 28, 56 | `n_estimators=500`, `learning_rate=0.03`, `max_depth=10`, `num_leaves=80` |

### MLForecast (LightGBM) models, interval

Interval models use intra-day lags aligned to the 15-minute frequency (96 intervals per day, 672 intervals per week).

| Tier | Lags | Parameters (Tuned) |
| :--- | :--- | :--- |
| LightGBM_Fast | 1, 96, 672 | `n_estimators=200`, `learning_rate=0.05`, `max_depth=6` |
| LightGBM_Standard | 1, 96, 672 | `n_estimators=400`, `learning_rate=0.05`, `max_depth=8` |
| LightGBM_Accuracy | 1, 96, 672 | `n_estimators=300`, `learning_rate=0.03`, `max_depth=10`, `num_leaves=80` |

### Exogenous feature encoding

Both pipelines generate calendar and Fourier features. The daily pipeline uses all features listed below; the interval pipeline omits `holiday_name_encoded`.

| Feature | Type | Description |
| :--- | :--- | :--- |
| `is_weekend` | Binary | Saturday or Sunday. |
| `is_holiday` | Binary | A US federal holiday (via the `holidays` library). |
| `is_holiday_week` | Binary | Within 3 days of a US holiday (`days_to_nearest_holiday <= 3`). |
| `holiday_name_encoded` | Integer | An integer encoding of the holiday name (0 if not a holiday). Daily pipeline only. |
| `is_month_start` | Binary | First day of the month. |
| `is_month_end` | Binary | Last day of the month. |
| `days_to_nearest_holiday` | Integer | Minimum calendar distance, in days, to any US holiday. |

Fourier features (daily pipeline): weekly (K=3, period 7) and yearly (K=3, period 365.25) harmonics, producing 12 sine and cosine columns.

Fourier features (interval pipeline): daily (K=3, period 96 intervals) and weekly (K=2, period 672 intervals) harmonics, producing 10 sine and cosine columns.

## Volume tiering

To analyze model performance across location sizes, the project uses dynamic, quartile-based volume tiering (Q1 through Q4).

1. Aggregation: calculate the mean sales per location across the training period.
2. Distribution: sort and split into four groups (quartiles).
3. Labels:
   - `Q1 (Low)`
   - `Q2`
   - `Q3`
   - `Q4 (High)`

This method ensures that tiers remain relative to the current benchmark population.

## Baseline and benchmarking

The primary baseline is `Baseline_Production` ([`BASELINE_MODEL`](../daily/config.py) in each `config.py`): the raw algorithmic projection, with zero-projection rows excluded so that evaluation focuses on intervals the baseline actively forecasted.

Both pipelines construct multiple baseline variants from the Snowflake extract:

| Variant | Formula | Zero-Projection Rows | Pipeline |
| :--- | :--- | :--- | :--- |
| `Baseline_Production` | `PROJECTION` (daily) or `Baseline_PROJECTION` (interval) | Excluded | Both |
| `Baseline_Adjusted_Draft` | `PROJECTION + USER_ADJUSTMENT` | Excluded | Both |
| `Baseline_Adjusted_Published` | `PROJECTION + PUBLISHED_USER_ADJUSTMENT` | Excluded | Both |
| `Baseline_ManagerOnly_Draft` | `PROJECTION + USER_ADJUSTMENT` where `IS_GENERATED_BY_MANAGER = TRUE` | Excluded | Daily only |
| `Baseline_ManagerOnly_Published` | `PROJECTION + PUBLISHED_USER_ADJUSTMENT` where `IS_GENERATED_BY_MANAGER = TRUE` | Excluded | Daily only |
| `Baseline_Production_Strict` | Same as Production | Included | Both |
| `Baseline_Adjusted_Draft_Strict` | Same as Adjusted_Draft | Included | Both |

All Nixtla models are compared against `Baseline_Production` in win and loss tables and in statistical significance tests.

---

## Statistical significance

Model-versus-baseline comparisons use a two-sided Wilcoxon signed-rank test on per-location MAE differences. A minimum of 10 common locations is required. p-values are not adjusted for multiple comparisons.

## Baseline data ingestion and Nixtla conversion

The benchmark pipelines consume pre-aggregated data from the Baseline ProductionForecastingService via Snowflake extracts. The tables below map the production system's internal domain model to the Nixtla-format DataFrames the benchmark uses.

### Production forecasting service domain model

The production forecasting system (`ProductionForecastingService`) generates projections via this service chain:

```
PostWeeklySessionRequest
  -> ForecastSessionOrchestrator
  -> ForecastSessionService
  -> ForecastSessionGenerator
  -> IForecastModelProvider.GetForecast()
  -> ForecastResponse { ForecastResult[] }
```

The primary algorithm is `SmartForecasting` (resolved via the `ProjectionModelType` enum). It fetches historical `PrecomputeData` from MongoDB, processes it through `SmartForecastDataProcessor`, and returns per-interval projections.

| Domain Entity | Property | Snowflake Extract Column | Nixtla Column |
| :--- | :--- | :--- | :--- |
| `DailySession` | `Projection` | `PROJECTION` (daily) | `y` (for `Baseline_Production`) |
| `IntervalForecast` | `Projection` | `Baseline_PROJECTION` (interval) | `y` (for `Baseline_Production`) |
| `DailySession` or `IntervalForecast` | `UserAdjustment` | `USER_ADJUSTMENT` | Combined with Projection for `Baseline_Adjusted_Draft`. |
| `DailySession` or `IntervalForecast` | `PublishedUserAdjustment` | `PUBLISHED_USER_ADJUSTMENT` | Combined with Projection for `Baseline_Adjusted_Published`. |
| `DailyForecastSession` | `IsGeneratedByManager` | `IS_GENERATED_BY_MANAGER` | Used to filter `Baseline_ManagerOnly_*` variants. |
| `DailySalesSummary` | `NetSales` | `ACTUAL_VALUE` (daily) or `NET_SALES` (interval) | `y` (for actuals) |
| `PrecomputeData` | `DailyTotalNetSales` | not applicable | Not directly used; feeds algorithms. |
| `PrecomputeDataPoint` | `NetSales`, `IntervalId` | not applicable | Not directly used; feeds algorithms. |

### Baseline hierarchy

Baseline forecasts are structured hierarchically:

```
WeeklyForecastSession (7 days)
  - DailySession[] (per day)
       - Projection (daily total, the sum of interval projections)
       - UserAdjustment (manager draft override)
       - HourlyForecast[] (per hour)
            - IntervalForecast[] (15-minute or 30-minute slots)
                 - Projection (per-interval algorithmic forecast)
                 - UserAdjustment
                 - PublishedUserAdjustment
```

The `Value` property on `DailySession` is computed as `Projection + UserAdjustment`.

### Snowflake extraction

Two SQL extracts bridge the production system's domain into flat CSVs the benchmark consumes:

[snowflake/daily_actual_vs_forecast.sql](../snowflake/daily_actual_vs_forecast.sql) joins `daily_forecast_sessions` (the latest session per
location-day, deduplicated by `created_on DESC, event_timestamp DESC`) with
`daily_interval_forecasts` (summing interval-level `projection`, `user_adjustment`,
and `published_user_adjustment` into daily totals) and `daily_sales_summary` (for `actual_value`).
The extract filters to `metric_id = 1` (NetSales).

[snowflake/interval_actual_vs_forecast.sql](../snowflake/interval_actual_vs_forecast.sql) joins the same `daily_forecast_sessions` with
`LATERAL FLATTEN` on the `interval_forecasts` BSON array to extract per-interval
`Baseline_PROJECTION`, `UserAdjustment`, and `PublishedUserAdjustment`. Actuals come
from `sales_ticket_with_interval`, aggregated to 15-minute slots via `SUM(net_sales)`.
`INTERVAL_ID_TICKS` is the .NET 100-nanosecond tick representation used as the join key
between the baseline forecast intervals and the actual sales intervals.

### Python ingestion wrappers

Each pipeline's data loader validates the Snowflake contract, coerces types, and converts to Nixtla format.

[daily/data_loader.py](../daily/data_loader.py)

| Function | Purpose |
| :--- | :--- |
| `load_daily_actual_vs_forecast()` | Reads `daily_actual_vs_forecast.csv`, validates all 10 expected columns, and coerces types (`ENTITY_UID` to string, `DAY_START_TIME` to datetime, booleans for manager flags). Strips whitespace from `ENTITY_UID` and normalizes dates to midnight. |
| `build_baseline_variants()` | Constructs 7 baseline variants by combining `PROJECTION`, `USER_ADJUSTMENT`, and `PUBLISHED_USER_ADJUSTMENT`. Filters on `PROJECTION > 0` for default variants; strict variants retain zeros. Manager-only variants additionally filter on `IS_GENERATED_BY_MANAGER = True`. Each variant is renamed to `[unique_id, ds, y]`. |
| `build_actuals()` | Maps `[ENTITY_UID, DAY_START_TIME, ACTUAL_VALUE]` to `[unique_id, ds, y]`. Zero-actual rows are preserved; filtering is deferred to the evaluation config. |
| `filter_eligible_locations()` | Returns composite UIDs with non-null actuals and `PROJECTION > 0`, requiring at least `TARGET_LOCATION_COUNT // 10` (30) distinct days per location. This is a lightweight Python-side guard; primary eligibility filtering happens in SQL. |

[interval/data_loader.py](../interval/data_loader.py)

| Function | Purpose |
| :--- | :--- |
| `load_interval_actual_vs_forecast()` | Reads `interval_actual_vs_forecast.csv`, validates 9 expected columns, and coerces types. Fills `NULL` net sales with `0.0`, treating missing intervals as zero-sales periods. |
| `split_train_test()` | Splits on `Baseline_PROJECTION` nullity: `NULL` becomes training data, `NOT NULL` becomes test data. Unlike the daily pipeline's date-based anchor split, the interval pipeline uses projection presence. |
| `build_baseline_variants()` | Constructs 5 baseline variants (no manager-only variants for the interval pipeline). Fills `NULL` projections and adjustments with `0.0` before summing. Each variant is renamed to `[unique_id, ds, y]`. |
| `build_actuals()` | Maps `[ENTITY_UID, INTERVAL_START_TS, NET_SALES]` to `[unique_id, ds, y]` from the test split only. |
| `to_nixtla_training()` | Maps `[ENTITY_UID, INTERVAL_START_TS, NET_SALES]` to `[unique_id, ds, y]` from the training split, providing the compact schema expected by the Nixtla libraries. |
